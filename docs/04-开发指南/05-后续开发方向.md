## 1. 微调GTE-Large-zh模型方案

### 目标
针对健身领域进行模型微调，提升领域特定的语义理解能力。

> **当前状态**: 已更换为 GTE-Large-zh 模型（相关性94.4%），基础性能已满足需求。

### 实施步骤
1. **数据准备**
   - 收集健身领域的query-document对
   - 构建正负样本对（相关/不相关动作）
   - 数据量目标：10,000+ 样本对

2. **微调方法**
   - 使用对比学习（Contrastive Learning）
   - 损失函数：InfoNCE Loss
   - 训练框架：sentence-transformers

3. **评估指标**
   - MRR@10（Mean Reciprocal Rank）
   - Recall@K（K=1,3,5,10）
   - 领域特定测试集准确率

### 预期收益
- 领域术语理解提升 20-30%
- 同义词/近义词匹配能力增强
- 减少语义歧义

## 2. 混合检索方案（BM25+向量）

### 目标
结合关键词匹配和语义检索的优势，提升召回率和准确率。

### 架构设计
```
用户查询
    ↓
┌───────────────────────────────────────┐
│  BM25检索（关键词）  │  向量检索（语义）  │
│      权重: 0.3       │      权重: 0.7     │
└───────────────────────────────────────┘
    ↓
RRF融合（Reciprocal Rank Fusion）
    ↓
最终排序结果
```

### 实施步骤
1. **BM25索引构建**
   - 使用Elasticsearch或Qdrant内置BM25
   - 索引字段：name_zh, name_en, description, steps

2. **融合策略**
   - RRF公式：`score = Σ 1/(k + rank_i)`
   - k值调优：通常取60

3. **权重调优**
   - 初始权重：BM25=0.3, 向量=0.7
   - 根据A/B测试结果调整

### 预期收益
- 精确匹配查询准确率提升 15-20%
- 长尾查询召回率提升 10-15%
- 减少"语义漂移"问题

## 3. 重排序模型方案

### 目标
在初步召回后使用Cross-Encoder进行精细排序，提升Top-K结果质量。

### 架构设计
```
向量检索（召回 top_k × 5）
    ↓
Cross-Encoder重排序
    ↓
返回 top_k 结果
```

### 模型选择
- **推荐模型**：`BAAI/bge-reranker-v2-m3`
- **备选模型**：`ms-marco-MiniLM-L-12-v2`

### 实施步骤
1. **模型部署**
   - 加载预训练Cross-Encoder
   - GPU加速推理

2. **集成方式**
   - 在Layer1向量检索后调用
   - 输入：query + 候选文档列表
   - 输出：重排序后的文档列表

3. **性能优化**
   - 批量推理
   - 缓存热门查询结果

### 预期收益
- Top-3准确率提升 10-15%
- 用户满意度提升
- 减少无关结果

### 注意事项
- 增加约50-100ms延迟
- 需要GPU资源
- 建议仅对top_k×3候选进行重排序

## 6. Agent模式架构演进（2026-01-06新增）

### 背景分析

#### 当前架构特点

当前DAML-RAG采用**三段式架构**：LLM决策 + 程序执行 + LLM综合

```
LLM选择模板 → 程序执行固定DAG → LLM综合结果
     ↓              ↓                ↓
   ~0.01元      ~0元(本地)        ~0.03元
```

**成本分析**（基于DeepSeek API）：
- 一次完整训练计划：~0.05元
- DAG编排：纯程序执行，0成本
- 主要成本：LLM选择(步骤6.5) + LLM综合(步骤10)

#### 当前架构优缺点

| 维度 | 优点 | 缺点 |
|------|------|------|
| 成本 | ✅ 极低（~0.05元/次） | - |
| 稳定性 | ✅ 执行可预测、无幻觉 | - |
| 速度 | ✅ 工具本地执行1-5ms | - |
| 灵活性 | - | ❌ 固定模板，无法动态调整 |
| 交互性 | - | ❌ 无法根据中间结果追问 |
| 商业化 | - | ❌ 成本太低，收费空间小 |

---

### Agent模式设计

#### 核心理念

让LLM根据用户需求**动态选择和执行工具**，而非固定DAG模板。

```
LLM理解意图 → LLM动态选择工具 → 执行 → LLM分析 → 继续/结束
     ↓              ↓            ↓         ↓
   ~0.02元       ~0.05元/轮    ~0元     ~0.05元/轮
```

#### 技术架构

```
┌─────────────────────────────────────────────────────────┐
│                    用户查询                              │
└─────────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────────┐
│              复杂度判断 + 会员等级检查                    │
└─────────────────────────────────────────────────────────┘
          ↓                              ↓
┌──────────────────────┐    ┌──────────────────────────────┐
│   标准模式（当前）     │    │   Agent模式（新增）           │
│   - 免费/暖心会员      │    │   - 能量会员专属              │
│   - 固定DAG模板       │    │   - LLM动态决策               │
│   - 成本~0.05元       │    │   - 成本~0.3-1元              │
│   - 快速响应          │    │   - 深度交互                  │
└──────────────────────┘    └──────────────────────────────┘
```

#### Agent模式执行流程（伪代码）

```python
async def agent_mode_execution(query: str, user_profile: dict):
    """
    Agent模式：LLM动态执行
    
    特点：
    - LLM自主决定调用哪些工具
    - 根据中间结果动态调整策略
    - 支持多轮推理和追问
    """
    
    # 1. LLM分析用户需求，生成初始执行计划
    plan = await llm_generate_plan(
        query=query,
        user_profile=user_profile,
        available_tools=MCP_TOOLS,  # 18个工具
        databases=["Neo4j", "Qdrant"]  # 三层检索
    )
    
    results = []
    
    # 2. 循环执行（最多5轮，防止无限循环）
    for round in range(5):
        # LLM选择下一步工具和参数
        tool_call = await llm_select_tool(
            plan=plan,
            previous_results=results,
            user_profile=user_profile
        )
        
        # 安全检查：验证工具调用合法性
        if not validate_tool_call(tool_call):
            break
        
        # 执行工具（本地调用，0成本）
        result = await execute_tool_safely(tool_call)
        results.append(result)
        
        # LLM判断是否需要继续
        decision = await llm_should_continue(
            goal=query,
            current_results=results
        )
        
        if decision.complete:
            break
        
        # 更新计划（根据结果调整）
        plan = decision.updated_plan
    
    # 3. LLM生成最终回答
    return await llm_generate_response(
        query=query,
        all_results=results,
        user_profile=user_profile
    )
```

### 技术风险与应对

| 风险 | 描述 | 应对措施 |
|------|------|----------|
| 幻觉风险 | LLM可能调用错误工具或生成虚假参数 | 工具调用白名单验证、参数范围检查、结果真实性验证 |
| 成本失控 | 复杂查询导致多轮调用，成本超预期 | 最大轮次限制(5轮)、单次成本上限(¥2)、实时监控告警 |
| 响应延迟 | 多轮LLM调用导致响应慢 | 流式输出中间结果、并行执行无依赖工具、缓存常见查询 |

---

### 总结

1. **当前架构**适合低成本、高稳定性场景
2. **Agent模式**适合高价值、需要灵活性的场景
3. **混合架构**是最佳选择：标准模式为主，Agent模式为付费增值
