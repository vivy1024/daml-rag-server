## 2. 文件命名规则

### 2.1 编号格式

- 一级目录：`XX-名称/`（两位数字，如 `01-快速开始/`）
- 二级目录：`XX-名称/`（两位数字，如 `01-系统架构/`）
- 文件：`XX-标题.md`（两位数字，如 `01-系统架构总览.md`）
- 编号必须连续，不允许跳号（如 01, 02, 03，不允许 01, 03, 05）
- 编号不允许重复（如同目录下不能有两个 03-xxx.md）

### 2.2 文件名格式

- 使用中文标题，简洁明了
- 不使用括号、特殊字符（如 `（已整合）`）
- 不使用版本号后缀（如 `-v1`、`-v2`）
- 用连字符 `-` 分隔词组（如 `01-系统架构总览.md`）

### 2.3 禁止的命名

| 禁止 | 原因 | 正确做法 |
|------|------|----------|
| `生产环境部署指南（已整合）.md` | 括号 + 状态后缀 | 删除，或合并到目标文档 |
| `01-MySQL数据库结构-v1.md` | 版本号后缀 | 用文档内 header 标注版本 |
| `04a-编排层/` | 字母后缀 | 重新编号 |
| `Neo4j图数据库架构评审报告.md` | 无编号 | 加编号或移到 07-测试报告 |

## 3. 文档 Header 规范

每篇文档开头必须包含：

```markdown
# 标题

**版本**: vX.Y.Z
**创建日期**: YYYY-MM-DD
**更新日期**: YYYY-MM-DD
**状态**: ✅ 已完成 | 🔄 持续更新 | 📋 规划中 | ⚠️ 已废弃

---
```

状态说明：
- `✅ 已完成` — 内容完整，与代码同步
- `🔄 持续更新` — 长期维护文档
- `📋 规划中` — 设计/调研阶段，未实施
- `⚠️ 已废弃` — 即将删除，内容已过时或已合并

## 4. 文档分类原则

### 放在哪个目录？

| 内容类型 | 目录 | 判断标准 |
|----------|------|----------|
| 架构设计 | 02-核心架构 | 回答"是什么"和"为什么" |
| 代码实现 | 03-代码参考 | 回答"怎么实现的"，含代码片段 |
| 使用指南 | 04-开发指南 | 回答"怎么用"，含操作步骤 |
| API 接口 | 05-API文档 | HTTP 接口定义、请求/响应格式 |
| 部署运维 | 06-部署运维 | 部署流程、环境配置、故障排查 |
| 测试/评审 | 07-测试报告 | 测试结果、评审报告、评估报告 |
| 调研/规划 | 04-开发指南 | 技术调研、未来规划（子目录 `05-调研规划/`） |

### 不应该存在的文档

- 纯占位文件（如"待补充"只有一行的 .md）
- 已整合的旧文档（应直接删除，不保留跳转说明）
- 一次性报告（如某次 bug 修复验证）超过 3 个月未更新的，考虑归档或删除

## 5. README.md 规范

每个目录必须有 `README.md`，内容：
- 该目录的简要说明（1-2 句）
- 文件列表（与实际文件一致，不多不少）

根目录 `docs/README.md` 额外包含：
- 项目概述
- 完整目录树（必须与实际文件结构一致）
- 快速导航

## 7. 维护流程

1. 新增文档前，先确认放在哪个目录，编号接续当前最大值 +1
2. 删除文档后，不需要重新编号已有文件（避免大量 git diff）
3. 每次代码大版本更新后，检查文档是否需要同步更新
4. 每季度做一次文档盘点，清理过时内容
