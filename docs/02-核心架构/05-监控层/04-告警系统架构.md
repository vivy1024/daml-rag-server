**版本**: v1.0.0  
**创建日期**: 2025-12-22  
**状态**: ✅ 已完成

---

## 概述

DAML-RAG的告警系统基于Prometheus和Alertmanager构建，提供实时的性能监控和异常告警能力。系统采用分级告警、智能路由和多渠道通知机制，确保关键问题能够及时发现和处理。

### 设计目标

1. **及时性** - 关键问题立即告警，避免延误
2. **准确性** - 合理的阈值和持续时间，减少误报
3. **可操作性** - 每个告警都有明确的处理步骤
4. **可扩展性** - 支持多种通知渠道和自定义规则
5. **智能化** - 告警分组、抑制和静默机制

## 告警系统架构

### 整体架构

```
指标采集层
    ↓
Prometheus（告警规则引擎）
    ├─ 性能瓶颈规则
    ├─ 错误率规则
    ├─ 资源使用规则
    ├─ 并发控制规则
    └─ 服务健康规则
    ↓
Alertmanager（告警管理器）
    ├─ 告警路由
    ├─ 告警分组
    ├─ 告警抑制
    └─ 告警静默
    ↓
通知渠道
    ├─ Webhook（DAML-RAG服务）
    ├─ Email（可选）
    ├─ Slack（可选）
    ├─ 企业微信（可选）
    └─ 钉钉（可选）
    ↓
Grafana Dashboard（可视化）
```

### 核心组件

#### 1. Prometheus告警规则引擎

**职责**：
- 定期评估告警规则（PromQL表达式）
- 检测指标是否超过阈值
- 触发告警并发送到Alertmanager

**配置文件**：
- `config/prometheus/prometheus.yml` - Prometheus主配置
- `config/prometheus/alerts/workflow_performance.yml` - 告警规则定义

#### 2. Alertmanager告警管理器

**职责**：
- 接收Prometheus发送的告警
- 根据路由规则分发告警
- 对告警进行分组、抑制和静默
- 发送通知到各个渠道

**配置文件**：
- `config/prometheus/alertmanager.yml` - Alertmanager配置
- `config/prometheus/templates/*.tmpl` - 告警通知模板

#### 3. 通知渠道

**支持的渠道**：
- Webhook：发送到DAML-RAG服务API
- Email：邮件通知
- Slack：Slack频道通知
- 企业微信：企业微信群通知
- 钉钉：钉钉群通知

## 告警规则设计

### 告警规则分类

系统定义了5大类告警规则，共25个告警：

| 分类 | 告警数量 | 评估间隔 | 说明 |
|------|---------|---------|------|
| **性能瓶颈** | 6个 | 30秒 | 工作流耗时、TTFB、步骤耗时 |
| **错误率** | 4个 | 30秒 | 失败率、LLM错误、缓存失效 |
| **资源使用** | 6个 | 30秒 | CPU、内存、连接池 |
| **并发控制** | 4个 | 30秒 | 并发数、队列长度、限流 |
| **服务健康** | 4个 | 30秒 | 服务可用性 |

### 1. 性能瓶颈告警

**目标**：及时发现性能问题，优化用户体验

| 告警名称 | PromQL表达式 | 阈值 | 持续时间 | 严重级别 |
|---------|-------------|------|---------|---------|
| WorkflowTotalDurationHigh | `workflow_total_duration_seconds > 30` | 30秒 | 1分钟 | warning |
| WorkflowStepDurationHigh | `workflow_step_duration_seconds > 1` | 1秒 | 1分钟 | warning |
| TTFBHigh | `workflow_ttfb_seconds > 5` | 5秒 | 1分钟 | warning |
| UserProfileLoadingHigh | `workflow_step_duration_seconds{step="1"} > 0.5` | 500ms | 1分钟 | warning |
| MembershipCheckHigh | `workflow_step_duration_seconds{step="3"} > 0.3` | 300ms | 1分钟 | warning |
| BGEClassificationHigh | `workflow_step_duration_seconds{step="4"} > 0.5` | 500ms | 1分钟 | warning |

**告警示例**：
```yaml
- alert: WorkflowTotalDurationHigh
  expr: workflow_total_duration_seconds > 30
  for: 1m
  labels:
    severity: warning
    category: performance
  annotations:
    summary: "工作流总耗时过高"
    description: "工作流总耗时 {{ $value }}秒，超过30秒阈值"
```

### 2. 错误率告警

**目标**：及时发现系统异常，保障服务可靠性

| 告警名称 | PromQL表达式 | 阈值 | 持续时间 | 严重级别 |
|---------|-------------|------|---------|---------|
| WorkflowFailureRateHigh | `(1 - workflow_success_rate) > 0.05` | 5% | 2分钟 | critical |
| LLMErrorRateHigh | `llm_error_rate > 0.05` | 5% | 2分钟 | critical |
| LLMFallbackCountHigh | `rate(llm_fallback_count[5m]) > 0.1` | 0.1/秒 | 2分钟 | warning |
| CacheMissRateHigh | `cache_miss_rate > 0.5` | 50% | 5分钟 | warning |

**告警示例**：
```yaml
- alert: WorkflowFailureRateHigh
  expr: (1 - workflow_success_rate) > 0.05
  for: 2m
  labels:
    severity: critical
    category: reliability
  annotations:
    summary: "工作流失败率过高"
    description: "工作流失败率 {{ $value | humanizePercentage }}，超过5%阈值"
```

### 3. 资源使用告警

**目标**：监控系统资源，避免资源耗尽

| 告警名称 | PromQL表达式 | 阈值 | 持续时间 | 严重级别 |
|---------|-------------|------|---------|---------|
| CPUUsageHigh | `process_cpu_percent > 70` | 70% | 3分钟 | warning |
| CPUUsageCritical | `process_cpu_percent > 90` | 90% | 1分钟 | critical |
| MemoryUsageHigh | `process_memory_percent > 80` | 80% | 3分钟 | warning |
| MemoryUsageCritical | `process_memory_percent > 95` | 95% | 1分钟 | critical |
| ConnectionPoolUsageHigh | `(connection_pool_active / (connection_pool_active + connection_pool_idle)) > 0.8` | 80% | 3分钟 | warning |
| ConnectionPoolWaitTimeHigh | `connection_pool_wait_time_seconds > 2` | 2秒 | 1分钟 | warning |

**告警示例**：
```yaml
- alert: CPUUsageCritical
  expr: process_cpu_percent > 90
  for: 1m
  labels:
    severity: critical
    category: resource
  annotations:
    summary: "CPU使用率严重过高"
    description: "CPU使用率 {{ $value }}%，超过90%阈值"
```

### 4. 并发控制告警

**目标**：监控并发请求，防止系统过载

| 告警名称 | PromQL表达式 | 阈值 | 持续时间 | 严重级别 |
|---------|-------------|------|---------|---------|
| ConcurrentRequestsHigh | `workflow_concurrent_requests > 80` | 80 | 2分钟 | warning |
| ConcurrentRequestsCritical | `workflow_concurrent_requests > 95` | 95 | 1分钟 | critical |
| QueueLengthHigh | `workflow_queue_length > 150` | 150 | 2分钟 | warning |
| RateLimitErrorsHigh | `rate(http_requests_total{status="429"}[5m]) > 0.1` | 0.1/秒 | 2分钟 | warning |

**告警示例**：
```yaml
- alert: ConcurrentRequestsCritical
  expr: workflow_concurrent_requests > 95
  for: 1m
  labels:
    severity: critical
    category: concurrency
  annotations:
    summary: "并发请求数严重过高"
    description: "当前并发请求数 {{ $value }}，接近系统上限"
```

### 5. 服务健康告警

**目标**：监控服务可用性，及时发现服务故障

| 告警名称 | PromQL表达式 | 阈值 | 持续时间 | 严重级别 |
|---------|-------------|------|---------|---------|
| ServiceDown | `up{job="daml-rag"} == 0` | 不可用 | 1分钟 | critical |
| RedisDown | `redis_up == 0` | 不可用 | 1分钟 | critical |
| MySQLDown | `mysql_up == 0` | 不可用 | 1分钟 | critical |
| Neo4jDown | `neo4j_up == 0` | 不可用 | 1分钟 | critical |

**告警示例**：
```yaml
- alert: ServiceDown
  expr: up{job="daml-rag"} == 0
  for: 1m
  labels:
    severity: critical
    category: availability
  annotations:
    summary: "DAML-RAG服务不可用"
    description: "DAML-RAG服务已停止响应"
```

## 告警分级机制

### 严重级别定义

系统定义了两个严重级别：

| 级别 | 标签值 | 含义 | 响应时间 | 示例 |
|------|--------|------|---------|------|
| **CRITICAL** | critical | 严重问题，需要立即处理 | 立即 | 服务不可用、失败率>5%、CPU>90% |
| **WARNING** | warning | 警告问题，需要关注 | 1小时内 | 耗时过高、缓存失效、CPU>70% |

### 分级策略

**CRITICAL级别触发条件**：
- 服务完全不可用
- 错误率超过5%
- 资源使用率超过90%
- 并发请求数接近系统上限

**WARNING级别触发条件**：
- 性能指标超过阈值但未严重影响服务
- 资源使用率超过70%但未达到危险水平
- 降级策略频繁触发

## 告警路由配置

### 路由策略

Alertmanager根据告警标签将告警路由到不同的接收器：

```
默认路由 (default)
├─ 严重告警 (severity: critical)
│  ├─ 接收器: critical-alerts
│  ├─ 分组等待: 0秒（立即发送）
│  └─ 重复间隔: 1小时
│
├─ 性能告警 (category: performance)
│  ├─ 接收器: performance-alerts
│  ├─ 分组等待: 30秒
│  └─ 重复间隔: 6小时
│
├─ 资源告警 (category: resource)
│  ├─ 接收器: resource-alerts
│  ├─ 分组等待: 1分钟
│  └─ 重复间隔: 6小时
│
├─ 并发告警 (category: concurrency)
│  ├─ 接收器: concurrency-alerts
│  ├─ 分组等待: 30秒
│  └─ 重复间隔: 3小时
│
└─ 可用性告警 (category: availability)
   ├─ 接收器: availability-alerts
   ├─ 分组等待: 0秒（立即发送）
   └─ 重复间隔: 30分钟
```

### 路由配置示例

```yaml
route:
  receiver: 'default'
  group_by: ['alertname', 'category', 'severity']
  group_wait: 10s
  group_interval: 10s
  repeat_interval: 12h
  
  routes:
    # 严重告警立即通知
    - match:
        severity: critical
      receiver: 'critical-alerts'
      group_wait: 0s
      repeat_interval: 1h
      
    # 性能告警
    - match:
        category: performance
      receiver: 'performance-alerts'
      group_wait: 30s
      repeat_interval: 6h
```

### 告警分组

**分组键**：`['alertname', 'category', 'severity']`

**分组效果**：
- 相同告警名称、分类和严重级别的告警会被分组
- 分组后的告警在一个通知中发送，避免告警轰炸
- 例如：多个实例的CPU告警会被分组为一个通知

## 告警抑制规则

### 抑制策略

告警抑制用于避免重复告警和告警轰炸：

#### 1. 服务不可用抑制其他告警

```yaml
- source_match:
    severity: 'critical'
    category: 'availability'
  target_match:
    severity: 'warning'
  equal: ['job']
```

**效果**：当服务不可用时，抑制该服务的所有警告级别告警

#### 2. 严重告警抑制警告告警

```yaml
# CPU严重告警抑制CPU警告
- source_match:
    alertname: 'CPUUsageCritical'
  target_match:
    alertname: 'CPUUsageHigh'
  equal: ['instance']

# 内存严重告警抑制内存警告
- source_match:
    alertname: 'MemoryUsageCritical'
  target_match:
    alertname: 'MemoryUsageHigh'
  equal: ['instance']
```

**效果**：当CPU使用率>90%时，不再发送CPU>70%的告警

## 告警升级策略

### 自动升级

**升级规则**：
1. **WARNING → CRITICAL**：如果警告级别告警持续超过30分钟未解决，自动升级为严重告警
2. **重复告警**：如果同一告警在1小时内重复触发3次，升级通知级别

**实现方式**：
- 通过Alertmanager的`repeat_interval`配置
- 通过Prometheus告警规则的`for`持续时间

### 人工介入

**介入时机**：
- 严重告警触发后15分钟未解决
- 同一告警在24小时内重复触发超过5次
- 多个关联告警同时触发

**介入方式**：
- 通过Grafana Dashboard查看详细指标
- 通过日志系统分析根因
- 通过Alertmanager Web界面管理告警

## 告警最佳实践

### 1. 合理设置阈值

**原则**：
- 基于历史数据设置阈值
- 避免过于敏感导致误报
- 避免过于宽松导致漏报

**示例**：
```yaml
# 不推荐：阈值过低，容易误报
- alert: WorkflowDurationHigh
  expr: workflow_total_duration_seconds > 5

# 推荐：基于P95分位数设置阈值
- alert: WorkflowDurationHigh
  expr: workflow_total_duration_seconds > 30
```

### 2. 设置合理的持续时间

**原则**：
- 瞬时波动不应触发告警
- 持续性问题应及时告警

**示例**：
```yaml
# 不推荐：立即告警，容易误报
- alert: CPUUsageHigh
  expr: process_cpu_percent > 70
  for: 0s

# 推荐：持续3分钟才告警
- alert: CPUUsageHigh
  expr: process_cpu_percent > 70
  for: 3m
```

### 3. 提供可操作的信息

**必须包含**：
- 清晰的告警摘要
- 详细的告警描述
- 相关的Dashboard链接
- 处理步骤文档链接

**示例**：
```yaml
annotations:
  summary: "工作流总耗时过高"
  description: "工作流总耗时 {{ $value }}秒，超过30秒阈值"
  runbook_url: "https://docs.example.com/runbooks/workflow-duration"
  dashboard_url: "http://localhost:3000/d/workflow-performance"
```

### 4. 避免告警疲劳

**策略**：
- 使用告警分组减少通知数量
- 使用告警抑制避免重复告警
- 设置合理的重复间隔
- 定期审查和调整告警规则

### 5. 测试告警规则

**测试方法**：
```bash
# 1. 验证规则语法
docker exec fitness_prometheus promtool check rules /etc/prometheus/alerts/workflow_performance.yml

# 2. 测试规则表达式
curl 'http://localhost:9090/api/v1/query?query=workflow_total_duration_seconds'

# 3. 手动触发告警
curl -X POST http://localhost:9093/api/v1/alerts -d '[
  {
    "labels": {"alertname": "TestAlert", "severity": "warning"},
    "annotations": {"summary": "测试告警"}
  }
]'
```

## 故障排查

### 常见问题

**1. 告警规则不生效**
- 检查规则文件语法：`promtool check rules alerts/workflow_performance.yml`
- 检查PromQL表达式是否正确
- 检查指标是否存在：访问Prometheus Web界面查询
- 检查标签匹配是否正确

**2. 告警未发送通知**
- 检查Alertmanager配置：`amtool check-config alertmanager.yml`
- 检查路由规则是否匹配
- 检查接收器配置是否正确
- 测试Webhook连接：`curl -X POST http://localhost:8001/api/alerts/webhook`

**3. 告警重复发送**
- 检查`repeat_interval`配置
- 检查告警是否频繁触发和恢复
- 调整告警规则的`for`持续时间

**4. 告警延迟**
- 检查Prometheus评估间隔（`evaluation_interval`）
- 检查告警规则的评估间隔（`interval`）
- 检查Alertmanager的`group_wait`配置
