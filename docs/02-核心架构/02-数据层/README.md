## 数据库协同架构

### 三层检索架构中的角色

```
Layer 1: 向量语义检索（Qdrant）
    ↓
Layer 2: 图谱关系推理（Neo4j）
    ↓
Layer 3: 业务规则约束（MySQL + Redis）
```

### 数据库特点对比

| 数据库 | 类型 | 主要用途 | 数据量 | 查询延迟 |
|--------|------|---------|--------|---------|
| **Neo4j** | 图数据库 | 知识图谱、关系推理 | 4,039节点 | <100ms |
| **Qdrant** | 向量数据库 | 语义检索、Few-Shot | 3,490+向量 | <50ms |
| **MySQL** | 关系数据库 | 用户数据、训练记录 | 动态增长 | <100ms |
| **Redis** | 缓存数据库 | 高速缓存、会话 | 内存限制 | <10ms |

## 数据流转示例

### 用户查询："推荐胸部训练动作"

**完整数据流**:

1. **Layer 1（Qdrant）**：
   - 将查询编码为1024维向量
   - 在`fitness_exercises_v2`集合中搜索
   - 返回Top-10相似动作的ID

2. **Layer 2（Neo4j）**：
   - 根据动作ID查询Exercise节点
   - 遍历TARGETS_PRIMARY关系找到目标肌肉
   - 遍历REQUIRES关系找到所需器材
   - 返回完整的动作信息

3. **Layer 3（MySQL + Redis）**：
   - 从MySQL查询用户档案（user_profiles表）
   - 检查用户的健身水平和可用器材
   - 应用业务规则过滤动作
   - 返回个性化推荐结果

## 数据同步机制

### Neo4j ↔ Qdrant

**同步方向**: Neo4j → Qdrant  
**同步内容**: Exercise节点、Food节点  
**同步频率**: 实时增量 + 每周全量

### MySQL ↔ Qdrant

**同步方向**: MySQL → Qdrant  
**同步内容**: 高质量对话（chat_sessions表）  
**同步频率**: 实时（评分≥4.0时） + 每天清理

### MySQL ↔ MCP服务

**同步方向**: 双向  
**同步内容**: 用户档案（user_profiles表）  
**同步频率**: 实时
