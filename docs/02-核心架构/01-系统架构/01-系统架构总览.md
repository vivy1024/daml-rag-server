## 📋 架构概览

DAML-RAG (Domain-Adaptive Multi-source Learning with RAG) 是面向垂直领域的自适应多源学习型RAG框架，实现了无幻觉、专业化、成本优化的智能问答系统。

```
┌─────────────────────────────────────────────────┐
│        DAML-RAG框架 (端口8001)                  │
├─────────────────────────────────────────────────┤
│  接口层 → 检索层 → 编排层 → 学习层 → 质量层       │
└─────────────────────────────────────────────────┘
```

**Docker服务**: `fitness_daml_rag`
**访问地址**: http://localhost:8001

## 🎯 核心设计理念

### 1. 推理时学习（In-Context Learning）

**原理**: 不修改模型权重，通过上下文注入实现学习

```
用户请求 →
检索历史成功案例 →
生成Few-Shot上下文 →
注入LLM调用 →
学习并响应
```

**优势**:
- ✅ 零训练成本
- ✅ 实时更新
- ✅ 领域自适应

### 2. 双模型协同（Teacher-Student）

**策略**: 云端教师教学 + 本地学生执行

| 场景 | 选择 | 原因 |
|-----|------|------|
| 冷启动 | 教师 | 无历史案例 |
| 质量下降 | 教师 | 需要高质量样本 |
| 相似度低 | 教师 | 新问题类型 |
| 常规请求 | 学生 | 已有成功经验 |

**成果**: 90%成本节省，质量保持

### 3. 知识图谱增强（GraphRAG）

**架构**: 结构化图谱 + 语义向量

```
结构化查询（Neo4j） + 语义搜索（Qdrant）
         ↓
    混合检索结果
         ↓
  精准推理 + 可解释
```

**数据规模 (2025-12-03实际状态)**:
- Neo4j 7.4.0 (端口7474/7687): ✅ 运行中
  - 3,654个节点 (Exercise: 1,603, Muscle: 94, Food: 1,880)
  - 46,276个关系 (TARGETS_PRIMARY: 559, CONTAINS_NUTRIENT: 44,406)
  - 100%图推理准确率
- Qdrant v1.11.0 (端口6333/6334): ✅ 运行中
  - 3,490个向量 (1024维 BGE-M3嵌入)
  - 训练知识: 43个向量
  - 健身动作: 1,596个向量
  - 食物营养: 1,851个向量
- Redis 7.2.5 (端口6379): ✅ 运行中 (会话管理)
- MySQL 8.4.0 (端口3306): ✅ 运行中 (用户数据、对话历史)

### 4. 质量保障（Multi-Dimensional QA）

**5维度评估**:

| 维度 | 权重 | 说明 |
|-----|------|------|
| 用户满意度 | 40% | 核心指标 |
| 响应正确性 | 30% | 准确性 |
| 响应完整性 | 15% | 完整度 |
| 工具使用 | 10% | 工具正确性 |
| 异常率 | 5% | 稳定性 |

**机制**:
- 统计显著性检验（t-test, Cohen's d）
- 渐进式降级策略
- 人工审核队列

### 4. DAG编排模式（DAG Orchestration）

DAG（有向无环图）编排是DAML-RAG系统的核心工作流管理机制：

```python
class DAGOrchestrator:
    """
    DAG编排器，负责根据DAG模板执行工具链
    """

    def __init__(self):
        self.templates = self._load_dag_templates()
        self.enhanced_orchestrator = EnhancedDAGOrchestrator()
        self.three_stage_orchestrator = ThreeStageOrchestrator()

    async def execute(self, query, user_id):
        # 步骤1: LLM选择DAG模板
        template = await self.select_dag_template(query)

        # 步骤2: 使用三段式编排器执行
        result = await self.three_stage_orchestrator.execute(
            template=template,
            query=query,
            user_id=user_id
        )

        return result

    async def select_dag_template(self, query):
        # 使用LLM决策引擎选择合适的DAG模板
        return await self.llm_decision_engine.select_template(query)
```

**8个DAG模板**：
1. **完整训练计划**（复杂度：高）
   - 工具流程：`get_user_profile` → `contraindications_checker` + `injury_risk_assessor` + `muscle_group_volume_calculator` → `intelligent_exercise_selector` → `professional_program_designer`
2. **营养规划**（复杂度：中）
   - 工具流程：`get_user_profile` → `tdee_calculator` → `nutrition_intake_analyzer` + `meal_plan_designer`
3. **安全评估**（复杂度：低）
   - 工具流程：`get_user_profile` → `contraindications_checker` + `injury_risk_assessor` → `safe_exercise_modifier`
4. **动作推荐**（复杂度：低）
   - 工具流程：`get_user_profile` → `contraindications_checker` → `intelligent_exercise_selector`
5. **训练量优化**（复杂度：中）
   - 工具流程：`get_user_profile` → `muscle_group_volume_calculator` → `movement_pattern_balancer` → `intelligent_weight_calculator`
6. **周期化设计**（复杂度：高）
   - 工具流程：`get_user_profile` → `muscle_group_volume_calculator` → `intelligent_exercise_selector` → `periodized_program_designer` → `training_split_designer`
7. **运动营养优化**（复杂度：中）
   - 工具流程：`get_user_profile` → `tdee_calculator` → `exercise_nutrition_optimization` → `meal_plan_designer`
8. **快速咨询**（复杂度：低）
   - 工具流程：`get_user_profile`

### 核心性能指标

| 指标 | 目标 | 实际 |
|-----|------|------|
| **响应延迟** | <100ms | <50ms |
| **并发能力** | 100 QPS | 200+ QPS |

| **成本节省** | >80% | 90%+ |

### 优化措施

#### 1. 三层检索性能优化

**Layer 1 (向量检索)**：
- 使用HNSW索引算法
- 优化索引参数（m=16, ef_construct=100）
- 向量维度：1024维BGE-M3
- 减少top_k召回数量（从3倍降至2倍）

**Layer 2 (图谱查询)**：
- 使用索引查询（MATCH with indexed properties）
- 限制MATCH深度（避免深度遍历）
- 使用LIMIT提前终止
- 使用参数化查询（避免查询计划缓存失效）

**Layer 3 (规则验证)**：
- 达到top_k后立即返回
- 缓存用户档案
- 简化规则逻辑
- 并行执行独立规则

#### 2. DAG编排并行执行优化

**并行执行策略**：
- 自动识别可并行执行的任务组
- 构建任务依赖图
- 按拓扑排序执行

**性能提升**：
- 理论加速比：6-10x（取决于DAG模板）
- 实际加速比：2-5x（考虑I/O开销）

#### 3. 智能缓存策略

**多级缓存架构**：
```
L1 内存缓存 (快速访问)
  ↓ 未命中
L2 Redis缓存 (持久化)
  ↓ 未命中
L3 计算缓存 (实时计算)
```

**工具特定缓存配置**：

| 工具类型 | TTL | 缓存级别 | 预加载 |
|---------|-----|---------|--------|
| 用户档案 | 1小时 | L2 Redis | ✅ |
| TDEE计算 | 30分钟 | L1 Memory | ✅ |
| 动作选择 | 10分钟 | L1 Memory | ✅ |
| 安全检查 | 5分钟 | L1 Memory | ❌ |
| 训练计划 | 不缓存 | L3 Computed | ❌ |

## ✅ 质量保证与专家验证体系

### 三轨评分体系

DAML-RAG系统采用三轨评分体系，确保输出质量：

| 评分维度 | 权重 | 说明 |
|---------|------|------|
| **用户体验** | 40% | 用户满意度和反馈 |
| **个性化适配** | 30% | 根据用户档案定制的程度 |
| **专家验证** | 30% | 专业知识的准确性和完整性 |

### 质量评估机制

**统计显著性检验**：
- 使用t-test检验不同模型/策略之间的性能差异
- 使用Cohen's d衡量效应大小
- 95%置信区间作为判断标准

**渐进式降级策略**：
- 当质量评分低于阈值时，自动降级到更保守的方法
- 例如：从复杂DAG模板降级到简单模板
- 确保用户始终得到可接受的响应

**人工审核队列**：
- 对评分较低的交互进行人工审核
- 收集专家反馈，改进系统
- 标注高质量对话用于Few-Shot学习和未来微调

### 专家验证流程

**多轮专家评审**：
1. **初审**：领域专家（健身教练、营养师）评估专业内容准确性
2. **复审**：系统架构师评估技术实现合理性
3. **终审**：用户体验专家评估整体可用性

**评审标准**：
- 专业性：内容是否符合运动科学和营养学原理
- 安全性：是否存在潜在的健康风险
- 可行性：建议是否适合用户实际情况
- 完整性：是否涵盖了用户查询的各个方面

**持续改进**：
- 定期收集用户反馈
- 分析低评分交互的根本原因
- 更新规则和模板
- 定期重新评估专家标准
